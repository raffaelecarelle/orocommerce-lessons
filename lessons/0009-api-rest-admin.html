Formazione OroCommerce · Lezione 09

REST API amministrativa

JSON:API, api.yml, e la tua entità esposta in lettura e scrittura in venti righe di configurazione.

Durata: ~75 min Prerequisiti: Lezione 8 Obiettivo: chiamare la tua entità via HTTP, autenticato

Perché si parte da qui

Collegare i sistemi del cliente (ERP/PIM) è il cuore della maggior parte dei progetti Oro, e il primo canale è quasi sempre la REST API. La buona notizia: in Oro le API non si scrivono, si dichiarano. Il controller, la serializzazione, i filtri, la paginazione, la validazione e la documentazione arrivano dalla piattaforma.

Cosa c'è di diverso dalle API di Magento

Le due API di Oro

Admin API — gli utenti del back-office, tutte le entità di gestione. Con la configurazione standard sta sotto /admin/api/, con la sandbox su /admin/api/doc, ed è configurata in Resources/config/oro/api.yml.

Storefront API — i customer user, un insieme di risorse molto più ristretto. Sta sotto /api/, sandbox su /api/doc, configurata in Resources/config/oro/api_frontend.yml. È la lezione 10.

I prefissi dipendono dalla configurazione del progetto: verificali sempre invece di fidarti di questa pagina — orobox console debug:router | grep rest_api.

JSON:API in tre minuti

Un formato con regole fisse, che Oro rispetta. Content type: application/vnd.api+json. Una risposta ha sempre questa forma:

{
  "data": {
    "type": "erpmappings",
    "id": "1",
    "attributes": {
      "erpCode": "ERP-1234",
      "oroSku": "SKU-001",
      "syncedAt": null
    },
    "relationships": { }
  }
}

Le convenzioni che userai ogni giorno:

Cosa vuoiCome si scrive
ElencoGET /admin/api/<alias-plurale>
Un recordGET /admin/api/<alias-plurale>/{id}
CrearePOST con corpo {"data": {"type": ..., "attributes": {...}}}
ModificarePATCH sullo stesso URL del record
Filtrare?filter[erpCode]=ERP-1234
Ordinare?sort=-syncedAt
Paginare?page[size]=20&page[number]=2
Scegliere i campi?fields[erpmappings]=erpCode,oroSku

Esporre un'entità

Si dichiara in Resources/config/oro/api.yml. Forma minima:

api:
    entities:
        Algoritma\Bundle\TrainingBundle\Entity\ErpMapping: ~

Da lì in poi la risorsa esiste, con tutte le azioni standard. Poi si restringe, che nei progetti reali è la parte importante:

api:
    entities:
        Algoritma\Bundle\TrainingBundle\Entity\ErpMapping:
            actions:
                delete: false
                delete_list: false
            fields:
                syncedAt:
                    description: Data dell'ultima sincronizzazione riuscita
            filters:
                fields:
                    erpCode:
                        data_type: string

Le chiavi che vedrai più spesso nel core: actions (abilita o disabilita get, get_list, create, update, delete, delete_list), fields (rinomina, escludi, documenta), filters, documentation_resource (un file Markdown con la descrizione della risorsa). Esempi reali: vendor/oro/platform/src/Oro/Bundle/UserBundle/Resources/config/oro/api.yml.

Autenticazione: OAuth 2.0

L'API non accetta la sessione del browser: serve un token. Oro include oro/oauth2-server, e il flusso più adatto a un ERP è client credentials — un'applicazione che parla con un'altra applicazione, senza utente interattivo.

POST https://<dominio>:<porta>/oauth2-token
Content-Type: application/json

{
  "grant_type": "client_credentials",
  "client_id": "<id generato>",
  "client_secret": "<secret generato>"
}

La risposta contiene access_token, da usare in ogni chiamata successiva come Authorization: Bearer <token>.

Il client si crea dal back-office in Sistema → Applicazioni OAuth (rotta /admin/oauth2/). Le chiavi RSA del server sono già state generate dall'installer; se mancano: orobox console oro:oauth-server:generate-keys.

Pratica: la tua entità via HTTP

  1. Dichiara la risorsa. src/Algoritma/Bundle/TrainingBundle/Resources/config/oro/api.yml:

    api:
    entities:
        Algoritma\Bundle\TrainingBundle\Entity\ErpMapping:
            actions:
                delete_list: false
            filters:
                fields:
                    erpCode:
                        data_type: string
    orobox console cache:clear
orobox console oro:api:cache:clear

  2. Trova l'alias assegnato. Non indovinarlo: chiedilo.

    orobox console oro:api:dump | grep -i erpmapping

    Ti risponde con l'entity type, cioè l'alias plurale usato nell'URL.

    Verificato: l'alias derivato non è quello che ti aspetti

    Provando questa lezione su un'installazione 7.0 CE, la classe Sandbox\Bundle\CheckBundle\Entity\SandboxMapping ha ricevuto l'alias checksandboxmappings — non sandboxmappings. La derivazione tiene conto anche del nome del bundle. Due conseguenze pratiche: non indovinare mai l'alias, e nei progetti reali dichiaralo esplicitamente, così l'URL non cambia se un domani rinomini una classe:

    api:
    entity_aliases:
        Algoritma\Bundle\TrainingBundle\Entity\ErpMapping:
            alias: erpmapping
            plural_alias: erpmappings

    Nei comandi curl qui sotto, sostituisci <alias-plurale> con quello che ti ha dato oro:api:dump (o con quello che hai dichiarato tu).

  3. Guarda la configurazione risolta. È il comando che userai per capire perché un campo non compare:

    orobox console oro:api:config:dump 'Algoritma\Bundle\TrainingBundle\Entity\ErpMapping'

  4. Apri la sandbox. https://<dominio>:<porta>/admin/api/doc, cerca la tua risorsa. Puoi provarla da lì, autenticato con la sessione del back-office: è il modo più veloce per vedere la forma esatta delle richieste.

  5. Crea un client OAuth. Back-office → Sistema → Applicazioni OAuth → nuova applicazione, tipo client credentials, associata a un utente. Annota client_id e client_secret: il secret si vede una volta sola.

  6. Chiama da riga di comando.

    BASE=https://<dominio>:<porta>      # l'URL stampato da `orobox up`

TOKEN=$(curl -sk -X POST "$BASE/oauth2-token" \
  -H 'Content-Type: application/json' \
  -d '{"grant_type":"client_credentials","client_id":"...","client_secret":"..."}' \
  | python3 -c 'import sys,json; print(json.load(sys.stdin)["access_token"])')

curl -sk "$BASE/admin/api/erpmappings" \
  -H "Authorization: Bearer $TOKEN" \
  -H 'Accept: application/vnd.api+json'

    Il flag -k serve perché il certificato dell'ambiente di sviluppo è autofirmato. Sostituisci l'alias con quello che ti ha dato oro:api:dump.

  7. Scrivi.

    curl -sk -X POST "$BASE/admin/api/erpmappings" \
  -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/vnd.api+json' \
  -d '{"data":{"type":"erpmappings","attributes":{"erpCode":"ERP-9001","oroSku":"SKU-009"}}}'

    Atteso: 201 Created e il record nel corpo. Verificalo anche nella griglia della lezione 5: è lo stesso dato, dalla parte opposta.

  8. Prova i permessi. Togli VIEW sulle mappature al ruolo dell'utente collegato al client OAuth e ripeti la GET. Atteso: 403. Questa è la proprietà più preziosa dell'API di Oro — gli ACL della lezione 6 valgono qui senza che tu abbia scritto nulla.

La vittoria di oggi

Un sistema esterno può leggere e scrivere le tue mappature, autenticato, filtrato e soggetto ai permessi, e tu hai scritto un file YAML di dieci righe. Questo è il pezzo dell'integrazione ERP che di solito si stima in giorni.

Verifica: rispondi a memoria

Cosa serve per esporre una tua entità nell'API amministrativa?

La dichiarazione basta: controller, serializzazione, filtri, paginazione e documentazione sono della piattaforma. Il lavoro vero è restringere con actions, fields e filters.

Qual è il Content-Type delle richieste di scrittura?

L'API segue JSON:API, quindi application/vnd.api+json. La richiesta del token OAuth invece è una normale application/json: sono due cose diverse.

Come sono protette le risorse dell'API amministrativa?

Stessi ACL, stessa ownership: un utente vede via API esattamente i record che vedrebbe nel back-office. È il motivo per cui la lezione 6 viene prima di questa.

Hai modificato api.yml e l'API non cambia. Cosa manca?

L'API ha una cache propria, oltre a quella del framework. La coppia da ricordare è cache:clear più oro:api:cache:clear; per la sandbox, oro:api:doc:cache:clear.

A memoria: scrivi l'URL per ottenere le prime 20 mappature ordinate per data di sincronizzazione decrescente, filtrate per codice ERP.

/admin/api/erpmappings?filter[erpCode]=ERP-1234&sort=-syncedAt&page[size]=20 — il meno davanti al campo in sort significa discendente.

Ripasso dalla lezione 8 (spaziatura): quali comandi usi per scoprire se il core pubblica un evento nel punto che ti interessa?

orobox console debug:event-dispatcher (tutti gli eventi e i loro listener), debug:event-dispatcher <nome> per uno solo, e grep -rn "dispatch(" vendor/oro/… per vedere dove viene lanciato nel codice.

Da leggere prima della prossima lezione

Fonte primaria

Oro — API Developer Guide, le pagine Configuration e Actions. È la sezione di documentazione Oro più densa e più utile: qui, a differenza che altrove, leggere la documentazione conviene più che leggere il core.

Se JSON:API ti è nuovo, dieci minuti su jsonapi.org/format (sezioni Document Structure e Fetching Data) ti risparmiano molti tentativi.

Esercizio fra una sessione e l'altra

  1. Disabilita l'azione delete sulla tua risorsa e verifica con curl -X DELETE che risponda 404 o 405. Poi riabilitala.
  2. Aggiungi un campo calcolato in sola lettura: dichiara in api.yml un campo isSynced con data_type: boolean e property_path verso un metodo isSynced() dell'entità che restituisce syncedAt !== null.
  3. Scrivi un file Resources/doc/api/erp_mapping.md e collegalo con documentation_resource. Riapri la sandbox: la tua descrizione deve comparire. È il tipo di dettaglio che fa la differenza quando l'API la usa il fornitore dell'ERP e non tu.
