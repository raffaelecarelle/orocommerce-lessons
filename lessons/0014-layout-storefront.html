Il layout dello storefront

Il secondo motore di rendering di Oro: dichiarativo, componibile, e l'unico modo per cambiare una pagina del negozio senza toccare il core.

Durata: ~60 min Prerequisiti: Lezione 4, Lezione 7 Obiettivo: aggiungere, spostare e togliere blocchi in una pagina storefront

Il debito che questa lezione paga

Nelle lezioni 5 e 6 hai scritto file dentro Resources/views/layouts/<tema>/config/ senza che nessuno ti spiegasse cosa fosse quella cartella. Era un debito voluto: serviva la datagrid, non tutto il sistema di rendering. Adesso si paga.

La domanda da cui parte tutto: perché il back-office si costruisce con normali template Twig, e lo storefront no?

Due motori, due pubblici

Il back-office ha pagine scritte da sviluppatori per sviluppatori e amministratori. Lo storefront è una vetrina che deve essere ricomponibile senza toccare il codice: tema scelto dal cliente, blocchi accesi e spenti dalla configurazione di sistema, contenuti piazzati dal web catalog. Un template Twig monolitico non regge quel carico.

Un controller storefront reale — nessun template, solo dati:

#[Route(path: '/view/{id}', name: 'oro_product_frontend_product_view', requirements: ['id' => '\d+'])]
#[Layout(vars: ['product_type', 'attribute_family', 'page_template'])]
public function viewAction(Product $product): array
{
    // ... restituisce ['data' => [...]], non una Response
}

Verificabile in vendor/oro/commerce/src/Oro/Bundle/ProductBundle/Controller/Frontend/ProductController.php. L'attributo è Oro\Bundle\LayoutBundle\Attribute\Layout.

La conseguenza che conta

Il controller non sa che aspetto avrà la pagina. Sa solo quali dati mette a disposizione. Chi decide la forma è l'albero dei blocchi, e quell'albero lo compone l'unione di tutti i file di layout attivi — quelli del core, quelli del tema, e i tuoi.

L'albero dei blocchi

Ogni pagina storefront è un albero. La radice si chiama root e la aggiunge il codice, non un file YAML:

// vendor/oro/platform/src/Oro/Bundle/LayoutBundle/Layout/LayoutManager.php
$layoutBuilder->add('root', null, 'root');

Da lì in giù è tutto dichiarativo. Lo scheletro che ti interessa davvero, nel tema default:

root
├─ head
│  └─ title, meta_charset, meta_viewport, styles, …
└─ body
   └─ wrapper
      └─ page_container
         └─ page_main
            └─ page_main_content
               ├─ page_main_header
               ├─ page_sidebar
               └─ page_content   ← qui finisce il contenuto della pagina

L'albero sopra è dichiarato con un solo @addTree in vendor/oro/platform/src/Oro/Bundle/UIBundle/Resources/views/layouts/default/page/layout.yml. Il customer portal ci aggiunge sopra i pezzi dello storefront (FrontendBundle/Resources/views/layouts/default/, cartelle page/ e oro_frontend_root/). page_content è il punto di aggancio più usato: quando non sai dove attaccare qualcosa, è la risposta di partenza.

Dove vive un layout

La convenzione è rigida e va imparata una volta sola:

Resources/views/layouts/
└─ <tema>/                            default, oppure un tema figlio
   ├─ theme.yml                        definizione del tema
   ├─ config/                          datagrids.yml, assets.yml, jsmodules.yml,
   │                                   images.yml, page_templates.yml
   ├─ imports/                         frammenti riutilizzabili
   ├─ page/                            layout comune a tutte le pagine
   └─ <nome_della_rotta>/              un cartella per rotta
      ├─ layout.yml                    layout update
      ├─ layout.html.twig              block theme
      └─ <altro_nome>.yml              altri update, stessa rotta

Il nome della cartella è il nome della rotta

Non un nome libero: oro_product_frontend_product_view/ è esattamente il name: dell'attributo #[Route]. Sbagli il nome, il file viene caricato senza errori e non succede nulla. È il primo posto dove guardare quando «non si vede niente».

Dentro una cartella-rotta i file YAML sono più di uno e si sommano tutti. Il core stesso lo fa: la pagina prodotto ha layout.yml, related_products.yml, upsell_products.yml, product_media.yml e altri. Un file per funzionalità, non un file per pagina.

Il layout update: cinque azioni

Un file di layout update è un elenco di azioni applicate all'albero. Queste cinque coprono quasi tutto:

AzioneCosa fa
@addaggiunge un blocco sotto un genitore
@addTreeaggiunge molti blocchi in una volta, con la loro gerarchia
@movesposta un blocco esistente sotto un altro genitore
@removetoglie un blocco dall'albero
@setOptioncambia un'opzione di un blocco già presente

A queste si aggiunge @setBlockTheme, che non tocca l'albero: dice quale file Twig contiene il markup dei tuoi blocchi.

layout:
    actions:
        - '@setBlockTheme':
            themes: '@AlgoritmaTraining/layouts/default/oro_product_frontend_product_view/training_notice.html.twig'

        - '@add':
            id: training_notice          # identificatore unico nell'intera pagina
            parentId: page_content       # sotto quale blocco
            siblingId: ~                 # accanto a quale fratello (~ = estremo)
            prepend: true                # prima del fratello, non dopo
            blockType: text              # che tipo di blocco
            options:
                text: 'Blocco aggiunto dal TrainingBundle'

E la coppia che serve quando devi ritoccare il core invece di aggiungere. Esempio reale, dal page template «wide» della pagina prodotto:

        - '@remove':
            id: attribute_group_rest
        - '@move':
            id: line_item_form_shopping_lists
            parentId: line_item_form
            siblingId: line_item_form_end
            prepend: true

File: …/ProductBundle/Resources/views/layouts/default/oro_product_frontend_product_view/page_template/wide/layout.yml.

Applicare un update solo a certe condizioni

Un update può avere una condizione, valutata sul contesto della pagina:

    conditions: 'context["filters_position"] == "sidebar"'

Se è falsa, l'intero file viene saltato. È così che il core accende e spegne intere porzioni di pagina in base alla configurazione di sistema, senza if sparsi nei template.

Riusare pezzi: gli import

layout:
    imports:
        -
            id: oro_product_list          # frammento in imports/oro_product_list/
            root: product_view_related_products_container
            namespace: related            # prefissa gli id importati

Il namespace esiste perché gli id dei blocchi sono unici in tutta la pagina: se importi due volte lo stesso frammento, senza namespace hai una collisione.

I dati: espressioni e data provider

Un valore che comincia con = è un'espressione, non una stringa. Due sorgenti:

  • context["…"] — le variabili di contesto della pagina (quelle dichiarate in #[Layout(vars: […])], più quelle di sistema).
  • data["…"] — i data provider: servizi che la vista può interrogare.
        - '@setOption':
            id: related_products
            optionName: items
            optionValue: '=data["oro_product_related_products"].getRelatedItems(data["product"])'

Un data provider tuo è un servizio normale con un tag. L'alias è obbligatorio: è il nome con cui lo chiami dentro data[…].

    oro_product.layout.data_provider.single_unit_mode:
        class: 'Oro\Bundle\ProductBundle\Layout\DataProvider\SingleUnitModeProvider'
        arguments:
            - "@oro_product.service.single_unit_mode"
        tags:
            - { name: layout.data_provider, alias: oro_product_single_unit_mode }

Un data provider non è un repository

Ci finisce la logica di presentazione: «questo blocco va mostrato?», «quali prodotti correlati?». Non ci va la logica di dominio, e soprattutto non ci vanno query pesanti senza cache: quel codice gira a ogni richiesta dello storefront, sulla pagina più visitata del sito.

Il markup: il block theme

Il blocco esiste nell'albero anche senza Twig. Il Twig decide solo come appare. La convenzione del nome del block è rigida: underscore, id del blocco, _widget.

{% block _training_notice_widget %}
    <div class="training-notice">{{ block_widget(block) }}</div>
{% endblock %}

block_widget(block) rende il contenuto predefinito del tipo di blocco. Lo ometti se vuoi rimpiazzare il contenuto invece di avvolgerlo.

Verificato eseguendo

Con @setBlockTheme la pagina prodotto rende <div class="training-notice">Blocco aggiunto dal TrainingBundle</div>. Commentando le due righe di @setBlockTheme e ripulendo la cache, il testo c'è ancora, nudo, senza il div. Il block theme non fa esistere il blocco: gli dà il vestito.

I tipi di blocco che userai

container (nessun markup proprio, serve a raggruppare), text, link, list e list_item, ordered_list, button e button_group, form e la famiglia form_*, fieldset, input. Più quelli strutturali che non aggiungi mai a mano: root, head, body, page_title, meta, script, style.

Temi

Un tema è una cartella sotto layouts/ con dentro theme.yml. Nel 7.0 Community il tema storefront predefinito è default, etichettato Refreshing Teal, e vive nel customer portal. I temi si ereditano:

# CMSBundle/Resources/views/layouts/optimized/theme.yml
parent: default
label: Optimized theme

Un tema figlio riceve tutti i layout update del padre e può aggiungerne, spostarne e toglierne. È il meccanismo con cui si fa il tema di un progetto: non si copia default, lo si eredita.

In ambiente dev puoi forzare il tema da URL con ?_theme=<nome> (ThemeListener, attivo solo con debug). Comodo per confrontare due temi sulla stessa pagina.

Page template

Alcune pagine hanno varianti scelte da back-office invece che da codice: la pagina prodotto ha tabs e wide. Sono cartelle sotto <rotta>/page_template/<chiave>/, e la variante attiva arriva nel contesto come page_template.

Da Magento: la mappa, e dove si rompe

Magento 2Oro
handle (catalog_product_view.xml)cartella con il nome della rotta
<container>blockType: container
<block class="…">blockType registrato + data provider
<referenceBlock remove="true">@remove
<move>@move
template .phtml del blockblock theme Twig, _<id>_widget
<update handle="…"/>imports

Dove l'analogia si rompe

  1. In Magento il block è una classe PHP con la logica dentro. In Oro il blockType è quasi sempre generico (container, text) e i dati arrivano da un data provider separato. Non scrivere una classe per ogni blocco: nella maggior parte dei casi non serve.
  2. Gli id dei blocchi Oro sono unici in tutta la pagina, non per contenitore. Le collisioni sono reali, per questo esiste il namespace negli import.
  3. Non c'è un equivalente di default.xml con la cascata per area: la composizione viene da tema padre, tema figlio, e condizioni sul contesto.

Pratica: un blocco tuo sulla pagina prodotto

Tutto quello che segue è stato eseguito su un'installazione 7.0 CE prima di finire in questa pagina. Il bundle è quello della lezione 2.

  1. Crea la cartella della rotta. Il nome non si inventa: è il name: della rotta storefront.

    mkdir -p src/Algoritma/Bundle/TrainingBundle/Resources/views/layouts/default/oro_product_frontend_product_view

  2. Scrivi il layout update, in …/oro_product_frontend_product_view/training_notice.yml:

    layout:
    actions:
        - '@setBlockTheme':
            themes: '@AlgoritmaTraining/layouts/default/oro_product_frontend_product_view/training_notice.html.twig'

        - '@add':
            id: training_notice
            parentId: page_content
            siblingId: ~
            prepend: true
            blockType: text
            options:
                text: 'Blocco aggiunto dal TrainingBundle'

  3. Scrivi il block theme, in …/oro_product_frontend_product_view/training_notice.html.twig:

    {% block _training_notice_widget %}
    <div class="training-notice">{{ block_widget(block) }}</div>
{% endblock %}

  4. Svuota la cache — i layout si risolvono a freddo, senza questo non vedi nulla.

    orobox console cache:clear --no-warmup

  5. Guarda la pagina. Prendi l'id di un prodotto pubblicato e apri https://<dominio>:<porta>/product/view/<id>. Il blocco deve comparire come prima cosa dentro page-content:

    <section class=" page-content" data-role="page-content">
    <div class="training-notice">Blocco aggiunto dal TrainingBundle</div>

  6. L'esperimento che insegna di più. Commenta le due righe di @setBlockTheme, svuota di nuovo la cache e ricarica. Il testo è ancora lì, senza il div: il blocco esiste comunque, il block theme gli dava solo il markup. Poi rimetti le righe a posto.

  7. Pulisci. Cancella le due cartelle create e svuota la cache. A differenza delle entità con #[Config] (lezione 3), qui non resta nulla in banca dati: il layout è solo file.

Diagnosi: quando non si vede niente

Quattro comandi, in ordine di utilità reale:

orobox console oro:debug:layout                      # contesto e configurazione risolta
orobox console oro:debug:layout --type=text          # opzioni di un tipo di blocco
orobox console oro:debug:layout --provider=<alias>   # firma di un data provider
orobox console oro:debug:layout:block-types          # tutti i tipi disponibili
orobox console oro:debug:layout:data-providers       # tutti i provider, con i metodi

--type=text stampa l'ereditarietà (block <- text) e la tabella delle opzioni con i valori predefiniti: è il modo più rapido per scoprire che un'opzione si chiama visible e non hidden, o viceversa.

La lista dei sospetti, in ordine

  1. Nome della cartella diverso dal nome della rotta. Silenzioso, frequentissimo.
  2. Cache non svuotata.
  3. parentId che non esiste su quella pagina.
  4. Tema sbagliato: hai scritto sotto default ma il sito usa un tema figlio che non eredita da lì.
  5. Un conditions: falso, che salta tutto il file senza dire niente.

La vittoria di oggi

Sai perché lo storefront ha un motore di rendering diverso, sai aggiungere, spostare e togliere un blocco senza toccare vendor/oro, e sai da dove arrivano i dati che un blocco mostra. Da qui in poi «cambiare la pagina prodotto» smette di essere una richiesta che ti fa paura.

Verifica: rispondi a memoria

Come si chiama la cartella di un layout update?

Il nome della rotta, esatto: oro_product_frontend_product_view/. Se sbagli il nome non arriva nessun errore, semplicemente non succede niente. È il primo sospetto quando «non si vede».

A cosa serve @setBlockTheme?

Solo il markup. Senza @setBlockTheme il blocco esiste lo stesso e rende il contenuto predefinito del suo tipo — verificato togliendolo e ricaricando la pagina. Il tema attivo si sceglie altrove; i block type si registrano con il tag layout.block_type.

Da dove prende i dati un blocco del layout?

Data provider, richiamati nelle espressioni come '=data["alias"].metodo()'. Il tag richiede l'alias, senza il quale il container solleva un errore in compilazione. Il contesto esiste ma serve ad altro: variabili di pagina, non dati di dominio.

Come si costruisce il tema di un progetto?

parent: default nel proprio theme.yml, come fa optimized nel CMSBundle. Copiare significa ereditare i bug e perdere ogni aggiornamento del core: è la stessa regola della lezione 7, applicata al frontend.

A memoria: hai un blocco del core che va tolto solo quando una certa opzione di sistema è attiva. Quali due meccanismi usi?

L'azione @remove con l'id del blocco, dentro un file di layout update che ha un conditions: valutato sul contesto. Se la condizione è falsa l'intero file viene saltato. Niente if nei template, niente override di file del core.

Ripasso dalla lezione 13 (spaziatura): l'ERP deve ricevere gli ordini appena vengono confermati. Quale dei canali di integrazione scegli, e perché non gli altri?

Message queue: l'evento è puntuale, il volume è basso per singolo messaggio, e il disaccoppiamento protegge il checkout se l'ERP è lento o giù. L'Integration bundle serve al flusso opposto, quando è Oro ad andare a prendere periodicamente; l'admin API va bene se è l'ERP a interrogare Oro, non il contrario; la storefront API non c'entra, non è il suo pubblico.

Da leggere dopo questa lezione

Fonte primaria

Oro — Layouts e Theming. Leggile con la pagina prodotto aperta accanto: la documentazione si capisce il doppio se hai un albero di blocchi vero davanti.

Esercizio fra una sessione e l'altra

  1. Aggiungi un blocco alla pagina di elenco prodotti (oro_product_frontend_product_index) che mostri un testo diverso a seconda di un'opzione: usa conditions: su una variabile di contesto che trovi con oro:debug:layout.
  2. Scrivi un data provider tuo — un servizio con il tag layout.data_provider — che restituisca un valore calcolato, e usalo in un @setOption. Verifica la firma con oro:debug:layout --provider=<alias>.
  3. Prendi una pagina storefront qualsiasi e ricostruisci su carta il suo albero dei blocchi leggendo solo i file YAML del core. Poi confronta con quello che vedi nel sorgente HTML. Le differenze che trovi sono le cose che ancora non sai del sistema: portale in chat.

Dove sei arrivato

Questa è l'ultima lezione del percorso. Hai l'ambiente, il bundle, le entità, il back-office, i permessi, l'estensione del core, i quattro canali di integrazione e adesso lo storefront.
