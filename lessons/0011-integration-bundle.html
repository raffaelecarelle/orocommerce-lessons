Integration bundle: canali, trasporti, connettori

Il framework con cui Oro va a prendere i dati da un sistema esterno — con la schermata di configurazione, le credenziali e lo storico già scritti da qualcun altro.

Durata: ~70 min Prerequisiti: Lezione 10 Obiettivo: una tua integrazione visibile e lanciabile dal back-office

Perché si parte da qui

Nelle due lezioni precedenti hai esposto i dati di Oro: l'ERP chiama, Oro risponde. Adesso si gira la freccia. Il catalogo sta nel gestionale, le giacenze stanno nel gestionale, e nessuno ha intenzione di scrivere un client HTTP che chiami Oro ogni notte. Tocca a Oro andare a prendere.

La domanda che decide tutto è sempre la stessa: chi inizia la conversazione? Se è il sistema esterno, il canale è l'API della lezione 9. Se è Oro, il canale è l'IntegrationBundle, ed è questa lezione.

Cosa ti dà, che altrimenti riscriveresti tu

  • Una schermata di configurazione in back-office, con la form dei parametri.
  • Le credenziali salvate su un'entità dedicata, non in un file di configurazione.
  • Lo storico di ogni sincronizzazione: quando, quanti record, con quali errori.
  • L'esecuzione manuale con un bottone, e quella schedulata dal cron.
  • La sincronizzazione parziale — solo ciò che è cambiato dall'ultima volta.

Sono cinque cose noiose e indispensabili. È il motivo per cui non si scrive un comando di console «che si collega all'ERP» e lo si schedula a mano: funziona, ma poi l'operatore non ha nessun posto dove guardare.

I tre pezzi, e cosa risponde ciascuno

PezzoDomandaTag del servizio
Channel type Che tipo di integrazione è? (etichetta, icona) oro_integration.channel
Transport Come ci si arriva, e con quali parametri? oro_integration.transport
Connector Che cosa si porta a casa? Uno per tipo di dato. oro_integration.connector

La sintassi dei tag, presa da un'integrazione vera che hai già nell'installazione (vendor/oro/crm-dotmailer/Resources/config/services.yml):

    tags:
        - { name: oro_integration.channel, type: dotmailer }
        - { name: oro_integration.transport, type: dotmailer_api, channel_type: dotmailer }
        - { name: oro_integration.connector, type: contact, channel_type: dotmailer }

Nota l'attributo channel_type sui due tag in basso: è quello che lega trasporto e connettori al loro canale. Un canale può avere più trasporti (REST oggi, SOAP domani) e quasi sempre ha più connettori, uno per entità sincronizzata.

Dove lo fa il core

La raccolta dei tag avviene in un compiler pass — lo strumento numero tre della lezione 7: vendor/oro/platform/src/Oro/Bundle/IntegrationBundle/DependencyInjection/CompilerPass/TypesPass.php. Leggilo: sono sessanta righe, e vedere il meccanismo che hai studiato in astratto usato sul serio vale più di qualunque spiegazione.

Le tre interfacce

Sono minuscole, ed è il punto: il framework chiede poco.

interface ChannelInterface
{
    public function getLabel();
}

interface TransportInterface
{
    public function init(Transport $transportEntity);
    public function getLabel();
    public function getSettingsFormType();
    public function getSettingsEntityFQCN();
}

interface ConnectorInterface
{
    public function getLabel(): string;
    public function getImportEntityFQCN();
    public function getImportJobName();
    public function getType();
}

Due metodi meritano una riga di spiegazione, perché il nome inganna:

  • getSettingsEntityFQCN() — il trasporto dichiara una propria entità in cui finiscono i parametri: URL, utenza, chiave. Estende Oro\Bundle\IntegrationBundle\Entity\Transport. È lì che vivono le credenziali, e per questo non stanno in un file .env: ogni istanza dell'integrazione ha le sue.
  • getImportJobName() — il connettore dichiara il nome del job batch che esegue la sincronizzazione. Il framework riusa l'infrastruttura di batch della piattaforma per eseguire il lavoro a lotti e tenere il conto dei record. A te serve conoscerne il nome, non scriverne uno da zero.

Le tre entità che vedrai in banca dati

EntitàCos'èChi la crea
ChannelL'integrazione configurata: nome, tipo, connettori attivi, abilitata o noL'utente, dal back-office
TransportI parametri di quella specifica integrazioneL'utente, nella stessa form
StatusL'esito di ogni esecuzione: connettore, data, conteggi, erroriIl framework, a ogni sync

Channel: la parola più sovraccarica di Oro

Channel qui è l'integrazione configurata. Ma channel type è il servizio che ne dichiara il tipo, e nel percorso funzionale «canale» indica tutt'altro. Quando scrivi un documento di analisi, dì «integrazione» per il record e «tipo di integrazione» per il servizio: ti eviterai una riunione di chiarimenti.

Pratica: la tua integrazione nel back-office

Costruiamo un'integrazione minima che porta dentro le mappature ERP. Il sistema esterno lo simuliamo con un file JSON dentro il progetto: il punto della lezione è il framework, non il protocollo. Quando al posto del file ci sarà un URL vero, cambierà solo il trasporto.

  1. Il channel type. Quattro righe, e non serve altro. 
    // src/Algoritma/Bundle/TrainingBundle/Integration/ErpChannelType.php
namespace Algoritma\Bundle\TrainingBundle\Integration;

use Oro\Bundle\IntegrationBundle\Provider\ChannelInterface;

class ErpChannelType implements ChannelInterface
{
    public function getLabel(): string
    {
        return 'algoritma.training.integration.erp.label';
    }
}

    L'etichetta è una chiave di traduzione, non una stringa: è la convenzione di tutto il core.

  2. Il trasporto e la sua entità di settings. L'entità estende Transport del core e aggiunge i campi che l'utente compilerà — qui il percorso del file. Serve anche un form type, che è quello della lezione 4: nessuno strumento nuovo.
  3. Il connettore. Estende AbstractConnector e dichiara cosa porta a casa. Il lavoro vero è l'iteratore che restituisce le righe una per volta: il framework le consuma a lotti, così un milione di record non finisce in memoria.
  4. Registra i tre servizi. In services.yml, con i tag visti sopra: 
        algoritma_training.integration.erp_channel:
        class: Algoritma\Bundle\TrainingBundle\Integration\ErpChannelType
        tags:
            - { name: oro_integration.channel, type: algoritma_erp }

    algoritma_training.integration.erp_transport:
        class: Algoritma\Bundle\TrainingBundle\Integration\ErpFileTransport
        tags:
            - { name: oro_integration.transport, type: algoritma_erp_file, channel_type: algoritma_erp }

    algoritma_training.integration.erp_mapping_connector:
        class: Algoritma\Bundle\TrainingBundle\Integration\ErpMappingConnector
        tags:
            - { name: oro_integration.connector, type: erp_mapping, channel_type: algoritma_erp }
  5. Verifica la registrazione prima di aprire il browser. 
    orobox console cache:clear
orobox console debug:container --tag=oro_integration.channel
orobox console debug:container --tag=oro_integration.connector

    Se il tuo canale non compare qui, non comparirà nemmeno in back-office: il problema è nel tag, non nell'interfaccia.

  6. Creala dal back-office. Sistema → Integrazioni, nuova integrazione, scegli il tuo tipo, compila i parametri del trasporto, seleziona i connettori, salva. Adesso esiste un record Channel: la configurazione non è nel codice, è un dato.
  7. Lanciala. Dal bottone della schermata, e poi da console — perché è così che girerà in produzione. 
    orobox console oro:cron:integration:sync --integration=<id>
orobox console oro:cron:integration:sync --integration=<id> --connector=erp_mapping

    L'id è quello che leggi nell'URL della schermata. Senza opzioni, il comando sincronizza tutte le integrazioni attive: è la forma con cui gira dal cron.

  8. Guarda lo storico. Nella schermata dell'integrazione, la scheda con l'esito delle esecuzioni. Adesso rompi il trasporto apposta — un percorso di file sbagliato — rilancia, e guarda cosa scrive. Quella schermata è l'unico posto in cui un operatore guarderà: se non ci arriva un messaggio comprensibile, l'integrazione non è finita.

Sincronizzazione completa e parziale

La prima esecuzione porta tutto. Le successive dovrebbero portare solo ciò che è cambiato, altrimenti ogni notte rileggi il catalogo intero per aggiornare tre prodotti. Il framework tiene per te la data dell'ultima sincronizzazione riuscita per connettore, nello Status: il connettore la legge e la usa per filtrare la richiesta al sistema esterno.

La trappola della sincronizzazione parziale

Filtrare per data di modifica funziona solo se il sistema esterno ha una data di modifica affidabile — e molti gestionali non ce l'hanno, o la aggiornano anche quando non cambia niente. Chiedilo prima di progettare il connettore. Se la risposta è no, la sincronizzazione completa notturna è una scelta legittima: dichiararla è meglio che scoprire in produzione che mancano dei record.

Verifica: rispondi a memoria

Quale tag registra il modo in cui si parla con il sistema esterno?

Il trasporto è il «come ci si arriva»: protocollo e parametri. Il channel_type nel tag lo lega al suo canale.

Dove finiscono le credenziali dell'ERP?

Il trasporto dichiara la propria entità con getSettingsEntityFQCN(). Così ogni istanza dell'integrazione ha i suoi parametri, e l'utente li cambia senza toccare un deploy.

L'ERP chiama Oro per aggiornare un record alla volta. Usi l'IntegrationBundle?

Integration è per quando è Oro ad andare a prendere. Se è il sistema esterno a iniziare la conversazione, l'API risponde già, con permessi e validazione inclusi. Usarlo al contrario è l'errore architetturale più comune nei primi progetti.

Il tuo canale non compare in «Sistema → Integrazioni». Cosa controlli per primo?

Prima la registrazione, poi tutto il resto: se debug:container --tag=oro_integration.channel non lo elenca, il compiler pass non lo ha visto, e nessuna schermata potrà mostrarlo.

A memoria: i tre pezzi di un'integrazione, e a quale domanda risponde ciascuno.

Channel type: che tipo di integrazione è (tag oro_integration.channel). Transport: come ci si arriva e con quali parametri, e possiede l'entità di settings con le credenziali (oro_integration.transport). Connector: che cosa si porta a casa, uno per tipo di dato (oro_integration.connector).

Ripasso dalla lezione 10 (spaziatura): cosa distingue la storefront API dall'admin API, oltre al file di configurazione?

Il request type, e quindi il pubblico: la storefront API risponde ai Customer User con i permessi dello storefront, l'admin API agli utenti interni con gli ACL del back-office. Stessa sintassi JSON:API, due mondi di sicurezza diversi — gli stessi due mondi del percorso funzionale.

Da leggere prima della prossima lezione

Fonte primaria

Oro — Integrations, in particolare Integration Configuration. Poi trenta minuti su vendor/oro/crm-zendesk/: è l'integrazione più piccola dell'installazione, e si legge per intero. Parti da Provider/ChannelType.php e segui i tag in Resources/config/services.yml.

Esercizio fra una sessione e l'altra

  1. Aggiungi un secondo connettore allo stesso canale — anche banale, che porta dentro una sola riga — e verifica che in back-office compaia come casella selezionabile. Poi disattivalo e rilancia la sync: il framework deve saltarlo.
  2. Fai fallire il trasporto in modo controllato (percorso inesistente) e fai in modo che il messaggio di errore nello storico dica cosa è andato storto, non «Exception». È la differenza fra un'integrazione consegnabile e una da assistenza continua.
  3. Leggi vendor/oro/platform/src/Oro/Bundle/IntegrationBundle/DependencyInjection/CompilerPass/TypesPass.php e portami la risposta a una domanda: cosa succede, esattamente, se dimentichi l'attributo type nel tag? Cerca l'eccezione, e dimmi a quale momento del ciclo di vita appartiene.
