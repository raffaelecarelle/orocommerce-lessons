Formazione OroCommerce · Lezione 09

Storefront API

La seconda API di Oro: stesso motore, pubblico diverso, e un modello di sicurezza che non perdona distrazioni.

Durata: ~50 min Prerequisiti: Lezione 8 Obiettivo: capire quando e come esporre dati al frontend

Perché esistono due API

Non è una duplicazione: sono due pubblici con due modelli di sicurezza diversi.

Admin APIStorefront API
Chi la usaERP, PIM, middleware, strumenti interniApplicazioni per i clienti: PWA, app mobile, portali
Chi si autenticaUser del back-officeCustomerUser, oppure visitatore ospite
ConfigurazioneResources/config/oro/api.ymlResources/config/oro/api_frontend.yml
Prefisso URL (configurazione standard)/admin/api//api/
Sandbox/admin/api/doc/api/doc
Risorse disponibiliQuasi tutte le entità di gestioneUn insieme ristretto e curato

Regola di sicurezza, non di stile

Una risorsa esposta sulla storefront API è raggiungibile da un cliente del negozio — e, se l'accesso ospite è attivo, potenzialmente da chiunque. Le mappature ERP della lezione 3 non vanno mai lì. Prima di aggiungere una riga a api_frontend.yml la domanda è: «un cliente del mio cliente ha diritto di vedere questo dato?»

Il request type: un motore, due configurazioni

Oro non ha due implementazioni di API. Ha un unico motore a processori, che lavora in un request type diverso: le richieste dello storefront portano il tipo frontend, e il sistema carica api_frontend.yml invece di api.yml, attivando e disattivando processori di conseguenza.

Verificabile nel codice del customer portal: vendor/oro/customer-portal/src/Oro/Bundle/FrontendBundle/Api/FrontendApiDependencyInjectionUtil.php, che abilita e disabilita processori per il tipo 'frontend'. Esempi di configurazione reali: vendor/oro/customer-portal/src/Oro/Bundle/CustomerBundle/Resources/config/oro/api_frontend.yml.

La conseguenza pratica: la sintassi che hai imparato nella lezione 8 vale identica. Cambia il file, cambia il pubblico, cambia il buon senso su cosa esporre.

Come si restringe una risorsa storefront

Il pattern che trovi in tutto il customer portal: risorsa in sola lettura, campi interni esclusi.

api:
    entities:
        Oro\Bundle\CustomerBundle\Entity\Customer:
            documentation_resource: '@OroCustomerBundle/Resources/doc/api_frontend/customer.md'
            actions:
                create: false
                update: false
                delete: false
                delete_list: false

E l'esclusione esplicita dei campi che non devono uscire:

            fields:
                public:
                    exclude: true
                selfManaged:
                    exclude: true

Il criterio giusto è l'elenco bianco

Sull'admin API puoi permetterti di esporre e poi restringere. Sulla storefront API si fa il contrario: si parte da nulla, si espone una risorsa alla volta, e per ciascuna si escludono esplicitamente i campi. Il costo di un errore è una fuga di dati, non un bug.

Autenticazione

Stesso server OAuth 2.0 della lezione 8, ma i client sono di tipo storefront e si creano in una sezione separata del back-office: la rotta è /admin/oauth2/frontend (oro_oauth2_frontend_index in debug:router). Un client storefront è legato a un CustomerUser, non a un utente del back-office.

Il flusso più usato qui è password o authorization code, perché c'è una persona che fa login — a differenza dell'integrazione ERP, dove usi client credentials. Il token endpoint resta POST /oauth2-token.

Esiste anche un accesso ospite, controllato dalla configurazione di sistema del customer portal: se attivo, alcune risorse (tipicamente catalogo e contenuti) rispondono senza token. Vale la pena verificarlo sempre su un progetto nuovo, prima di dare per scontato che l'API sia chiusa.

Pratica: esplorare invece di esporre

Questa lezione non aggiunge risorse tue: l'esercizio giusto è imparare a leggere quello che c'è, perché è così che lavorerai su un progetto reale.

  1. Elenca le risorse storefront.

    orobox console oro:api:dump --request-type=frontend | head -40

    Confronta il numero di risorse con quelle dell'admin API (oro:api:dump senza opzioni). La differenza è il punto della lezione.

  2. Apri la sandbox storefront. https://<dominio>:<porta>/api/doc. Cerca products: guarda quali campi ci sono e quali no rispetto all'entità Product che vedi nel back-office.

  3. Leggi una configurazione reale.

    cat vendor/oro/customer-portal/src/Oro/Bundle/CustomerBundle/Resources/config/oro/api_frontend.yml

    Domande da tenere in mente mentre leggi: quali azioni sono disabilitate? Quali campi sono esclusi, e perché proprio quelli?

  4. Confronta la stessa entità sulle due API.

    orobox console oro:api:config:dump 'Oro\Bundle\CustomerBundle\Entity\Customer'
orobox console oro:api:config:dump 'Oro\Bundle\CustomerBundle\Entity\Customer' --request-type=frontend

    Stessa entità, due configurazioni risolte diverse. È la dimostrazione concreta del request type.

  5. Chiamata da ospite. Prova senza token:

    BASE=https://<dominio>:<porta>      # l'URL stampato da `orobox up`

curl -sk -i "$BASE/api/products?page[size]=1" \
  -H 'Accept: application/vnd.api+json' | head -20

    Se risponde 401, l'accesso ospite è disattivato su quell'installazione; se risponde 200, è attivo. In entrambi i casi hai imparato qualcosa che su un progetto reale devi sapere prima di andare in produzione.

La vittoria di oggi

Sai che le API di Oro sono due, sai distinguerle in dieci secondi guardando il file di configurazione, e sai porti la domanda giusta prima di esporre qualcosa. Nelle revisioni di sicurezza questa è la differenza fra un progetto che passa e uno che torna indietro.

Verifica: rispondi a memoria

Quale file configura le risorse della storefront API?

api_frontend.yml, stessa cartella di api.yml. Il motore è lo stesso: cambia il request type della richiesta, e con esso il file di configurazione caricato.

Chi si autentica sulla storefront API?

Il pubblico sono i clienti del negozio: CustomerUser, e in alcune configurazioni gli ospiti. I client OAuth storefront si creano in una sezione separata, /admin/oauth2/frontend.

Quale criterio si usa per esporre risorse sullo storefront?

Elenco bianco, risorsa per risorsa, con esclusione esplicita dei campi interni. Il costo di un errore qui non è un bug: è un dato riservato pubblicato.

Come confronti la configurazione di un'entità fra le due API?

oro:api:config:dump <classe> e lo stesso comando con --request-type=frontend: due configurazioni risolte a confronto, ed è il modo più rapido per capire cosa esce davvero.

A memoria: due differenze sostanziali (non di URL) fra admin API e storefront API.

Il soggetto autenticato (User del back-office contro CustomerUser o ospite) e il criterio di esposizione (restringere il molto contro esporre il minimo). Segue da entrambe una terza differenza: l'insieme di risorse disponibili è molto più piccolo sullo storefront.

Ripasso dalla lezione 8 (spaziatura): quali due cache vanno svuotate dopo una modifica alla configurazione dell'API?

orobox console cache:clear (framework) e orobox console oro:api:cache:clear (configurazione API). Per la sandbox, anche oro:api:doc:cache:clear.

Da leggere prima della prossima lezione

Fonte primaria

Oro — Storefront API e Storefront API Routes. Venti minuti, e leggile con in mente il progetto del cliente: la domanda utile è «cosa di questo progetto passerà da qui?».

Esercizio fra una sessione e l'altra

  1. Crea un client OAuth storefront per un customer user di prova (i dati demo ne contengono) e ottieni un token. Poi chiama /api/customerusers/… e osserva quali campi ricevi.
  2. Prendi una risorsa storefront a tua scelta e scrivi, in cinque righe, cosa non espone rispetto all'entità completa. Portami l'elenco: ragionare su cosa il core ha deciso di nascondere è il modo più rapido per imparare il criterio.
  3. Domanda di architettura, da discutere insieme: l'ERP del cliente deve leggere i prezzi. Passa dall'admin API o dalla storefront API? Perché? Non c'è una risposta sola, ci sono ragioni migliori e peggiori.
