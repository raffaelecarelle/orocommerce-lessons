Message queue

Topic, producer, processor, consumer: il lavoro in background di Oro, e il motivo per cui l'integrazione ERP ci gira sopra.

Durata: ~70 min Prerequisiti: Lezione 11 Obiettivo: un tuo messaggio prodotto e consumato

Perché si parte da qui

Un webhook dell'ERP non può aspettare trenta secondi mentre ricalcoli i prezzi. Una sincronizzazione notturna non può girare dentro una richiesta HTTP. La risposta di Oro è la message queue: chi riceve l'evento mette un messaggio in coda e risponde subito; un processo separato lo esegue.

Non è un'infrastruttura opzionale: in Oro ci girano già l'indicizzazione della ricerca, gli la sincronizzazione delle integrazioni, il ricalcolo dei prezzi, le notifiche email. Quando aggiungi il tuo lavoro asincrono, ti inserisci in un meccanismo che è già il cuore dell'applicazione.

Community Edition: nessuna infrastruttura in più

In CE il trasporto è DBAL: la coda è una tabella PostgreSQL. In Enterprise si usa RabbitMQ. Il codice che scrivi è identico: cambia solo la configurazione del trasporto. Nota pratica: il trasporto su database funziona a polling, quindi un messaggio può partire con qualche secondo di ritardo — normale, non è un bug.

I quattro concetti

ConcettoCos'èDove vive
TopicIl tipo di messaggio, con il contratto del suo payloadClasse in Async/Topic/
ProducerChi invia il messaggioServizio oro_message_queue.client.message_producer
ProcessorChi esegue il lavoroClasse in Async/, registrata con un tag

Il topic: un contratto, non una stringa

In Oro il topic è una classe che estende AbstractTopic e dichiara la forma del payload con un OptionsResolver. È una scelta di design importante: i messaggi malformati falliscono quando li pubblichi, non tre ore dopo dentro al consumer.

class CreateOpenApiSpecificationTopic extends AbstractTopic
{
    #[\Override]
    public static function getName(): string
    {
        return 'oro.api.create_open_api_specification';
    }

    #[\Override]
    public static function getDescription(): string
    {
        return 'Creates OpenAPI specification.';
    }

    #[\Override]
    public function configureMessageBody(OptionsResolver $resolver): void
    {
        $resolver
            ->setRequired('entityId')
            ->setAllowedTypes('entityId', 'int');
    }
}

Sorgente: vendor/oro/platform/src/Oro/Bundle/ApiBundle/Async/Topic/CreateOpenApiSpecificationTopic.php. I topic si registrano in Resources/config/mq_topics.yml con il tag oro_message_queue.topic, di solito applicato a tutto il file con _defaults.

Il processor: tre esiti possibili

Un processor implementa due interfacce: MessageProcessorInterface (fa il lavoro) e TopicSubscriberInterface (dichiara a quali topic è iscritto). Il valore restituito decide il destino del messaggio:

CostanteSignificatoQuando
ACKFatto, rimuovi dalla codaSuccesso
REJECTNon processabile, scartaMessaggio non valido: riprovare non aiuta
REQUEUERimetti in codaProblema temporaneo: ERP irraggiungibile, lock occupato

Le costanti stanno in vendor/oro/platform/src/Oro/Component/MessageQueue/Consumption/MessageProcessorInterface.php. Scegliere fra REJECT e REQUEUE è la decisione di progetto più importante del codice asincrono: un REQUEUE su un errore permanente crea un ciclo infinito.

Pratica: sincronizza una mappatura in background

  1. Il topic. src/Algoritma/Bundle/TrainingBundle/Async/Topic/SyncErpMappingTopic.php:

    <?php

declare(strict_types=1);

namespace Algoritma\Bundle\TrainingBundle\Async\Topic;

use Oro\Component\MessageQueue\Topic\AbstractTopic;
use Symfony\Component\OptionsResolver\OptionsResolver;

class SyncErpMappingTopic extends AbstractTopic
{
    #[\Override]
    public static function getName(): string
    {
        return 'algoritma.training.sync_erp_mapping';
    }

    #[\Override]
    public static function getDescription(): string
    {
        return 'Segna una mappatura ERP come sincronizzata.';
    }

    #[\Override]
    public function configureMessageBody(OptionsResolver $resolver): void
    {
        $resolver
            ->setRequired('mappingId')
            ->setAllowedTypes('mappingId', 'int');
    }
}

  2. Il processor. src/Algoritma/Bundle/TrainingBundle/Async/SyncErpMappingProcessor.php:

    <?php

declare(strict_types=1);

namespace Algoritma\Bundle\TrainingBundle\Async;

use Algoritma\Bundle\TrainingBundle\Async\Topic\SyncErpMappingTopic;
use Algoritma\Bundle\TrainingBundle\Entity\ErpMapping;
use Doctrine\Persistence\ManagerRegistry;
use Oro\Component\MessageQueue\Client\TopicSubscriberInterface;
use Oro\Component\MessageQueue\Consumption\MessageProcessorInterface;
use Oro\Component\MessageQueue\Transport\MessageInterface;
use Oro\Component\MessageQueue\Transport\SessionInterface;
use Psr\Log\LoggerInterface;

class SyncErpMappingProcessor implements MessageProcessorInterface, TopicSubscriberInterface
{
    public function __construct(
        private ManagerRegistry $doctrine,
        private LoggerInterface $logger
    ) {
    }

    #[\Override]
    public static function getSubscribedTopics(): array
    {
        return [SyncErpMappingTopic::getName()];
    }

    #[\Override]
    public function process(MessageInterface $message, SessionInterface $session): string
    {
        $body = $message->getBody();
        $manager = $this->doctrine->getManagerForClass(ErpMapping::class);
        $mapping = $manager->find(ErpMapping::class, $body['mappingId']);

        if (null === $mapping) {
            $this->logger->warning('Mappatura {id} non trovata', ['id' => $body['mappingId']]);

            return self::REJECT;
        }

        $mapping->setSyncedAt(new \DateTime());
        $manager->flush();

        $this->logger->info('Mappatura {id} sincronizzata', ['id' => $body['mappingId']]);

        return self::ACK;
    }
}

    Nota il REJECT sul record inesistente: riprovare non lo farebbe comparire.

  3. Registra topic e processor. Resources/config/mq_topics.yml:

    services:
    _defaults:
        tags:
            - { name: oro_message_queue.topic }

    Algoritma\Bundle\TrainingBundle\Async\Topic\SyncErpMappingTopic: ~

    Resources/config/mq_processors.yml:

    services:
    _instanceof:
        Oro\Component\MessageQueue\Client\TopicSubscriberInterface:
            tags:
                - { name: oro_message_queue.client.message_processor }

    Algoritma\Bundle\TrainingBundle\Async\SyncErpMappingProcessor:
        arguments:
            - '@doctrine'
            - '@logger'

    E nell'Extension: $loader->load('mq_topics.yml'); e $loader->load('mq_processors.yml');. Il costrutto _instanceof è la stessa scorciatoia che usa AttachmentBundle: tagga automaticamente ogni servizio del file che implementa quell'interfaccia.

  4. Pubblica il messaggio. Un comando è il modo più rapido per provarlo. Aggiungi al comando della lezione 3, o creane uno nuovo, questa dipendenza e questa riga:

    use Oro\Component\MessageQueue\Client\MessageProducerInterface;

// costruttore: private MessageProducerInterface $producer

$this->producer->send(SyncErpMappingTopic::getName(), ['mappingId' => $id]);

    Nel services.yml, l'argomento è '@oro_message_queue.client.message_producer'.

  5. Verifica che il topic sia registrato.

    orobox console cache:clear
orobox console oro:message-queue:topics | grep algoritma

  6. Avvia il consumer in un terminale e lascialo girare:

    orobox console oro:message-queue:consume -vv

    In un secondo terminale lancia il comando che pubblica il messaggio. Nel primo devi vedere il messaggio ricevuto e processato; nel database, synced_at valorizzato.

    orobox console doctrine:query:sql "SELECT id, erp_code, synced_at FROM algoritma_erp_mapping"

  7. Prova il fallimento. Pubblica un mappingId inesistente (es. 999999) e guarda il consumer: REJECT, warning nel log, messaggio non ripubblicato. Poi prova a mandare un payload sbagliato — per esempio una stringa al posto dell'intero — e osserva che l'errore arriva in fase di pubblicazione: è il contratto del topic che fa il suo lavoro.

La vittoria di oggi

Hai un canale asincrono tuo, con un contratto esplicito sul payload e una gestione dei fallimenti pensata. È lo schema con cui costruirai la sincronizzazione ERP vera: un webhook che pubblica, un consumer che lavora, e il processo HTTP che resta veloce.

Il consumer va riavviato dopo ogni modifica al codice

È un processo PHP di lunga durata: il codice che ha in memoria è quello di quando è partito. Se cambi il processor e non riavvii, continuerai a vedere il comportamento vecchio e a dare la colpa alla cache. In produzione il consumer è gestito da un supervisor che lo fa ripartire.

Verifica: rispondi a memoria

Cosa definisce la classe Topic in Oro?

Nome (getName()) e contratto del payload (configureMessageBody() con un OptionsResolver). Il processor si iscrive al topic dichiarandone il nome in getSubscribedTopics().

Un ERP è irraggiungibile durante il consumo. Cosa restituisci?

REQUEUE: il problema è temporaneo. REJECT si usa quando riprovare non può funzionare (payload non valido, record inesistente). ACK su un fallimento fa perdere il lavoro in silenzio.

Su Community Edition, dove vive la coda?

Trasporto DBAL su PostgreSQL. RabbitMQ è Enterprise. Il codice non cambia: cambia la configurazione del trasporto, e con essa la latenza (il DBAL fa polling).

Hai modificato il processor ma il comportamento è quello vecchio. Perché?

Il consumer è un processo di lunga durata: va riavviato. È l'errore numero uno di chi inizia a lavorare con le code.

A memoria: i quattro concetti della message queue e chi fa cosa.

Topic: nome e contratto del payload. Producer: pubblica (oro_message_queue.client.message_producer). Processor: esegue e restituisce ACK / REJECT / REQUEUE. Consumer: il processo oro:message-queue:consume che estrae i messaggi e li smista ai processor iscritti.

Ripasso dalla lezione 11 (spaziatura): i tre pezzi che compongono un'integrazione in Oro, e quale dei tre contiene le credenziali dell'ERP.

Channel (il tipo di integrazione, tag oro_integration.channel), transport (come ci si arriva, oro_integration.transport), connector (che cosa si porta a casa, oro_integration.connector). Le credenziali stanno nel transport: è l'entità di settings che l'utente compila in back-office, non una costante nel codice.

Esercizio fra una sessione e l'altra

  1. Fai pubblicare il messaggio automaticamente: un doctrine.orm.entity_listener su ErpMapping, evento postPersist, che invia SyncErpMappingTopic. Attenzione: dentro un listener Doctrine non si fa flush — pubblica e basta, il lavoro lo farà il consumer.
  2. Aggiungi al payload del topic un campo opzionale force (booleano, default false) e usalo nel processor per risincronizzare anche chi ha già syncedAt. Verifica che un payload con un tipo sbagliato venga rifiutato alla pubblicazione.
  3. Leggi vendor/oro/platform/src/Oro/Bundle/IntegrationBundle/Async/ e individua come la sincronizzazione della lezione 11 usa la coda. Portami la catena: chi pubblica, chi consuma, e dove si vede l'avanzamento nel back-office.
